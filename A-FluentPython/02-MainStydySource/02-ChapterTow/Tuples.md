```text
Tuples as Immutable Lists

The Python interpreter and standard library make extensive use of tuples as immutable lists, and so should you. This brings two key benefits:

Clarity
    When you see a tuple in code, you know its length will never change.

Performance
    A tuple uses less memory than a list of the same length, and it allows Python to do some optimizations.

However, be aware that the immutability of a tuple only applies to the references contained in it. References in a tuple cannot be deleted or replaced. But if one of those references points to a mutable object, and that object is changed, then the value of the tuple changes. The next snippet illustrates this point by creating two tuples-a and b-which are initially equal. Figure 2-4 represents the initial layout of the b tuple in memory.

When the last item in b is changed, b and a become different:
```
>>> a = (10, 'alpha',)
>>> b = (10, 'alpha',)
>>> a == b
True
>>> b[-1].append(99)
>>> a == b
False
>>> b
(10, 'alpha',)

Tuples with mutable items can be a source of bugs. As we'll see in "What Is Hashable" on page 84, an object is only hashable if its value cannot ever change. An unhashable tuple cannot be inserted as a dict key, or a set element.

If you want to determine explicitly if a tuple (or any object) has a fixed value, you can use the hash built-in to create a fixed function like this:

>>> def fixed(o):
...     try:
...         hash(o)
...     except TypeError:
...         return False
...     return True
...
>>> tf = (10, 'alpha', (1, 2))
>>> tm = (10, 'alpha',)
>>> fixed(tf)
True
>>> fixed(tm)
False
```
```text
We explore this issue further in "The Relative Immutability of Tuples" on page 207.

Despite this caveat, tuples are widely used as immutable lists. They offer some performance advantages explained by Python core developer Raymond Hettinger in a StackOverflow answer to the question: "Are tuples more efficient than lists in Python?". To summarize, Hettinger wrote:

• To evaluate a tuple literal, the Python compiler generates bytecode for a tuple constant in one operation; but for a list literal, the generated bytecode pushes each element as a separate constant to the data stack, and then builds the list.

• Given a tuple t, tuple(t) simply returns a reference to the same t. There's no need to copy. In contrast, given a list l, the list(l) constructor must create a new copy of l.

• Because of its fixed length, a tuple instance is allocated the exact memory space it needs. Instances of list, on the other hand, are allocated with room to spare, to amortize the cost of future appends.

• The references to the items in a tuple are stored in an array in the tuple struct, while a list holds a pointer to an array of references stored elsewhere. The indirection is necessary because when a list grows beyond the space currently allocated, Python needs to reallocate the array of references to make room. The extra indirection makes CPU caches less effective.

Comparing Tuple and List Methods

When using a tuple as an immutable variation of list, it is good to know how similar their APIs are. As you can see in Table 2-1, tuple supports all list methods that do not involve adding or removing items, with one exception-tuple lacks the __reversed__ method. However, that is just for optimization; reversed(my_tuple) works without it.
```

وعلى الرغم من هذا التحذير، تُستخدم الـ tuples على نطاق واسع كقوائم غير قابلة للتعديل [cite: 66]. وهي تقدم بعض مزايا الأداء التي شرحها مطور بايثون الأساسي **رايموند هيتينجر (Raymond Hettinger)** في إجابة على موقع StackOverflow على سؤال: "هل الـ tuples أكثر كفاءة من القوائم في بايثون؟" [cite: 66]. وباختصار، كتب هيتينجر [cite: 66]:

* لتقييم الـ tuple النصية (literal)، يقوم مترجم بايثون بتوليد كود بايت (bytecode) لـ tuple ثابتة في **عملية واحدة** [cite: 67]؛ ولكن بالنسبة للـ list النصية، فإن كود البايت المولد يقوم بدفع (pushes) كل عنصر كمتغير ثابت منفصل إلى مكدس البيانات (data stack)، ثم يقوم ببناء القائمة [cite: 67].
* بالنظر إلى tuple تسمى `t`، فإن استدعاء المشيد `tuple(t)` يعيد ببساطة **مرجعاً لنفس الكائن `t`** [cite: 67]؛ فلا حاجة للنسخ [cite: 67]. في المقابل، بالنظر إلى قائمة `l`، فإن مشيد القوائم `list(l)` يجب أن ينشئ نسخة جديدة تماماً من `l` [cite: 67].
* بسبب طولها الثابت، يتم تخصيص مساحة الذاكرة التي تحتاجها الـ tuple **بالظبط وبدون أي زيادة** [cite: 67]. ومن ناحية أخرى، يتم تخصيص مثيلات الـ list مع **مساحة إضافية شاغرة**، لتوزيع وتخفيف تكلفة عمليات الإضافة (`append`) المستقبلية [cite: 67].
* يتم تخزين مراجع العناصر في الـ tuple داخل مصفوفة في هيكل الـ tuple نفسه (struct) [cite: 68]، بينما تحتفظ القائمة (list) بمؤشر (pointer) يشير إلى مصفوفة مراجع مخزنة في مكان آخر في الذاكرة [cite: 68]. وهذا التوجيه غير المباشر (indirection) ضروري لأنه عندما تنمو القائمة خارج المساحة المخصصة لها حالياً، تحتاج بايثون إلى إعادة تخصيص مصفوفة المراجع لإفساح المجال [cite: 68]. وهذا التوجيه غير المباشر الإضافي يجعل كاش المعالج (CPU caches) أقل فاعلية [cite: 68].

**مقارنة طرق الـ Tuple والـ List (ص. 34):** [cite: 68]

عند استخدام الـ tuple كبديل غير قابل للتعديل للـ list، فمن الجيد معرفة مدى تشابه واجهات البرمجية (APIs) الخاصة بهما [cite: 68]. كما ترى في الجدول 2-1، تدعم الـ tuple جميع طرق الـ list التي لا تتضمن إضافة أو إزالة عناصر، باستثناء واحد — حيث تفتقر الـ tuple إلى طريقة `__reversed__` [cite: 68]. ومع ذلك، فإن هذا لغرض التحسين فقط؛ حيث تعمل الدالة المدمجة `reversed(my_tuple)` بشكل ممتاز وبدونها [cite: 68].

### 🏛️ 1. عدم القابلية "النسبية" للتعديل (The Relative Immutability) ⛓️

#### 👶 الشرح المبسط (من 0% لـ 100%):
تخيل إن الـ Tuple عبارة عن **"علبة كرتون"** مقسمة لثلاث خانات [cite: 194]، وجوا كل خانة حطينا **"رابط أو حبل مطاطي"** (Reference) بيربط قطعة في الخارج [cite: 63, 194].
بايثون بتضمن لك ضمانة حديدية إن **الحبال المطاطية دي لا يمكن فكها، ولا قطعها، ولا تبديلها بغيرها** [cite: 63, 194]! 

* الخانة الأولى مربوطة بـ **رقم** `10` [cite: 64]. (الرقم ثابت ومستحيل يتغير) [cite: 64].
* الخانة الثانية مربوطة بـ **نص** `'alpha'` [cite: 64]. (النص ثابت ومستحيل يتغير) [cite: 64].
* الخانة الثالثة مربوطة بـ **قائمة (List)** تحتوي على `` [cite: 64]. 

**وهنا تقع المفاجأة الكبرى 🚨:**
الحبل المطاطي في الخانة الثالثة بيفضل رابط نفس القائمة دي ومستحيل يسيبها [cite: 63, 194]. لكن القائمة نفسها هي كائن **قابل للتعديل (Mutable)** [cite: 194, 529]! 
يعني إيه؟ يعني تقدر تمد إيدك جوه القائمة دي (اللي بره العلبة) وتضيف جواها رقم جديد زي `99` [cite: 64, 196]!
لما تعمل كده (`b[-1].append(99)`) [cite: 64]:
* الحبل المطاطي لسه سليم ورابط نفس القائمة [cite: 196].
* لكن محتوى القائمة اتغير وبقى `` [cite: 65, 196]!
* وبما إن القائمة اتغيرت، قيمة الـ Tuple الكلية اتغيرت وبقت مختلفة عن التوبل `a` [cite: 64, 196]!

وهذا هو معنى **عدم القابلية "النسبية"** [cite: 66, 194]؛ الـ Tuple كـ كبائن مراجع محصنة وثابتة [cite: 194]، ولكن لو المرجع بيشير لكائن مرن، فالقيمة النهائية للتوبل ممكن تهتز وتتغير [cite: 63, 194]!

### 🔑 2. لغز الهاش (What Is Hashable?) والقفل الأمني 🔒

#### 👶 الشرح المبسط (من 0% لـ 100%):
بايثون عندها شروط أمنية صارمة جداً عشان تقبل تحط كائن كـ **مفتاح في القاموس (`dict`)** أو كـ **عنصر في المجموعة (`set`)** [cite: 65, 538]. 
الشرط هو: **"لازم الكائن يكون له كود بصمة ثابت (Hash Code) مستحيل يتغير طول حياته عشان بايثون تعرف مكانه في الذاكرة"** [cite: 65, 538].

* الـ Tuple اللي كلها حاجات ثابتة زي: `tf = (10, 'alpha', (1, 2))` [cite: 66]
  * بايثون بتفحصها: الخانة 1 ثابتة، والـ 2 ثابتة، والـ 3 (وهي توبل داخلية) ثابتة [cite: 66, 143]. 
  * النتيجة: الكائن ده **أمين وقابل للهاش (`fixed(tf) -> True`)** [cite: 66]، وينفع نستخدمه كمفتاح قاموس [cite: 65].
  
* الـ Tuple اللي في أخرها قائمة مرنة زي: `tm = (10, 'alpha',)` [cite: 66]
  * بايثون بتفحصها: "يا خبر! في نهايتك قائمة ممكن تتغير في أي لحظة! كود البصمة بتاعك هيهتز ويتغير" [cite: 65]!
  * النتيجة: الكائن **غير آمن ومرفوض للهاش (`fixed(tm) -> False`)** [cite: 66]! لو حاولت تحطه كمفتاح قاموس بايثون هتصرخ فوراً وترفض [cite: 65]!

### ⚡ 3. لماذا الـ Tuple أسرع وأقوى من الـ List في الذاكرة؟ (أسرار رايموند هيتينجر) 🚀

رايموند هيتينجر، أحد كبار مطوري بايثون، كشف عن أربعة أسرار مذهلة تشرح تفوق الـ Tuple كفاءةً [cite: 66]:

#### **السر الأول: سرعة الـ Bytecode في سطر واحد ⚙️**
* لما تكتب كود: `t = (1, 2, 3)`
  * بايثون أثناء ترجمة الكود (Compile time) بتفهم إن الكائن ده ثابت، فبتبنيه كـ **قيمة ثابتة جاهزة (Constant)** في الذاكرة في خطوة واحدة كودية [cite: 67].
* لما تكتب كود: `l =`
  * بايثون ما تقدرش تثبته في مرحلة الترجمة [cite: 67]! بتضطر تولد كود بايت يلف على عنصر عنصر، ويدفعهم (push) للـ Stack واحد ورا التاني، وبعدين تجمعهم وتعمل الـ list [cite: 67]! (عملية أبطأ بكتير) [cite: 67].

#### **السر الثاني: خدعة النسخ المجاني (`tuple(t)`) 🪄**
* لو عندك توبل `t` وحبيت تعمل منها توبل جديدة: `t2 = tuple(t)` [cite: 67]. 
  * بايثون بتقولك: "ما هي كده كده ثابتة وما بتتغيرش! خذ نفس العنوان في الذاكرة ووفر وقتك ومساحتك!" (`t2 is t -> True`) [cite: 67, 216].
* لكن لو عندك قائمة `l` وحبيت تعمل كود: `l2 = list(l)` [cite: 67].
  * بايثون مجبرة تنسخ كل العناصر في كائن جديد تماماً في الذاكرة لأن القائمة ممكن تتعدل في أي لحظة [cite: 67]!

#### **السر الثالث: تفصيل الذاكرة على المقاس بالظبط (No Spare Room) 📏**
* القائمة `list` دايماً بتطلب من الذاكرة **مساحة أكبر من حجمها الحقيقي** [cite: 67]. لو القائمة فيها 3 عناصر، بايثون بتحجز مكان لـ 6 عناصر [cite: 67]. ليه؟ عشان لو حبيت تعمل `append` مستقبلاً تلاقي مكان فاضي وم تضطرش تنقل القائمة كلها لمكان جديد في الذاكرة في كل مرة [cite: 67, 115].
* الـ `tuple` طولها ثابت ومعروف [cite: 63]. فبايثون بتحجز ليها مساحة في الذاكرة **على قد الـ 3 عناصر بالظبط وبدون أي هدر** [cite: 67].

#### **السر الرابع: طريق الذاكرة المباشر (Cache Friendliness) 🧠**
* في مفسر بايثون المكتوب بلغة C:
  * **الـ Tuple:** بتخزن مراجع عناصرها في مصفوفة مدمجة **داخل نفس كائن التوبل نفسه** في الذاكرة [cite: 68]. المعالج (CPU) بيقراها دفعة واحدة وبسرعة فائقة لأن البيانات قريبة جداً من بعضها [cite: 68].
  * **الـ List:** بتحتوي على **مؤشر** (Pointer) يشير لمصفوفة تانية موجودة في مكان بعيد تماماً في الذاكرة [cite: 68]. التشتت ده (Indirection) بيخلي الـ CPU كاش يفقد فاعليته وتكون القراءة أبطأ [cite: 68].

# BRA

# 2 Data about Tokyo: name, year, population (thousands), population change (%), and area (km²).
# 3 A list of tuples of the form (country_code, passport_number).
# 4 As we iterate over the list, passport is bound to each tuple.
# 5 The % formatting operator understands tuples and treats each item as a separate field.
# 6 The for loop knows how to retrieve the items of a tuple separately-this is called "unpacking." Here we are not interested in the second item, so we assign it to _, a dummy variable.

However, in a match/case statement, _ is a wildcard that matches any value but is not bound to a value. See "Pattern Matching with Sequences" on page 38. And in the Python console, the result of the preceding command is assigned to _ unless the result is None.

## 🛠️ أولاً: وضع الاستخراج والترجمة (ص. 36 - 37)

### **النص الأصلي (Original English Text):**

```text
Using * to Grab Excess Items

Defining function parameters with *args to grab arbitrary excess arguments is a classic Python feature.

In Python 3, this idea was extended to apply to parallel assignment as well:

>>> a, b, *rest = range(5)
>>> a, b, rest
(0, 1,)
>>> a, b, *rest = range(3)
>>> a, b, rest
(0, 1,)
>>> a, b, *rest = range(2)
>>> a, b, rest
(0, 1, [])

In the context of parallel assignment, the * prefix can be applied to exactly one variable, but it can appear in any position:

>>> a, *body, c, d = range(5)
>>> a, body, c, d
(0,, 3, 4)
>>> *head, b, c, d = range(5)
>>> head, b, c, d
(, 2, 3, 4)
```

### **الترجمة العربية الدقيقة:**

**استخدام الـ * لتجميع العناصر الزائدة (Using * to Grab Excess Items) — (ص. 36):** [cite: 5, 46]

يعد تعريف معاملات الدوال باستخدام `*args` لتجميع الوسائط الزائدة العشوائية (arbitrary excess arguments) ميزة كلاسيكية معروفة في بايثون [cite: 46].

وفي الإصدار Python 3، تم تمديد وتوسيع هذه الفكرة لتنطبق على التعيين المتوازي (parallel assignment) أيضاً [cite: 46]:

```python
>>> a, b, *rest = range(5)
>>> a, b, rest
(0, 1,)

>>> a, b, *rest = range(3)
>>> a, b, rest
(0, 1,)

>>> a, b, *rest = range(2)
>>> a, b, rest
(0, 1, [])
``` [cite: 46]

وفي سياق التعيين المتوازي، يمكن تطبيق البادئة `*` على **متغير واحد فقط بالتمام والكمال**، ولكن يمكن لهذا المتغير أن يظهر في **أي موضع** [cite: 46]:

```python
>>> a, *body, c, d = range(5)
>>> a, body, c, d
(0,, 3, 4)

>>> *head, b, c, d = range(5)
>>> head, b, c, d
(, 2, 3, 4)
``` [cite: 47]

### 🚨 4. القوانين الأمنية الصارمة للـ `*` في بايثون
عشان كودك ما يضربش ويطلع أخطاء، بايثون حاطة قانونين في غاية الأهمية [cite: 46, 59]:

1. **قانون المتغير الواحد (Single Star Variable):**
   غير مسموح إطلاقاً بكتابة أكتر من متغير معاه `*` في نفس سطر التفكيك [cite: 46]! 
   * ❌ **ممنوع:** `a, *body, *rest, c = range(5)` (بايثون هتتوه ومش هتعرف مين يلم إيه!).
   * **الاستثناء الوحيد (ص. 45):** لو عندك مجموعات متداخلة (Nested Sequences)، ينفع تحط `*` واحدة جوه المجموعة الخارجية و `*` واحدة جوه المجموعة الداخلية [cite: 59].
2. **الناتج دايماً قائمة (Always a List):**
   مهما كان نوع المتتالية الأصلية اللي بتفككها (سواء كانت `tuple` أو `range` أو حتى نصوص `str`)، فإن المتغير المسبوق بـ `*` **دايماً هيرجعلك البيانات في صورة قائمة (`list`)** [cite: 46].
